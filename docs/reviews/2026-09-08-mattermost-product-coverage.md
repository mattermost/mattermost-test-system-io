# Mattermost product-behavior coverage audit — eight exact PR snapshots

This bounded, read-only audit finds useful existing regressions, but **full-suite selection is not proof that the changed behavior has an assertion**. The clearest gaps are plain-number phone autolinking (#38345), actual SAML certificate rotation through uploads and peer handling (#38383), and a few attachment-policy API branches (#38328). Pin/unpin and plugin-body changes have direct server regressions. The markdown-image PR repairs external test data and adds no product behavior.

No product tests, product code, Impact Gate mappings, or configuration were edited. No tests were run and no per-test CI or TSIO execution artifacts were inspected in this audit. Every “assertion present” below means source inspection at the cited revision; every suggested mapping is **static, unreviewed, and unexecuted**. This report does not assert eight PRs passed, that their checks ran these tests, or that their mergeability is established.

### #38229 — Apply request body size limit to plugin requests (merged)

**Exact change:** The cap applies specifically when cookie-authenticated, non-GET CSRF validation must read the body because the CSRF header is absent. Its limit is `MaximumPayloadSizeBytes + bytes.MinRead`. A `http.MaxBytesError` produces 413 without plugin dispatch; other body-read errors produce 500. Header-CSRF, non-cookie and GET paths retain their streaming/bypass behavior. Calling this a universal plugin-request cap would misstate the implementation. [limit and status handling](https://github.com/mattermost/mattermost/blob/4196a5a222e5536bc93584dcead452df138eee4b/server/channels/app/plugin_requests.go#L271); [scope and body restoration](https://github.com/mattermost/mattermost/blob/4196a5a222e5536bc93584dcead452df138eee4b/server/channels/app/plugin_requests.go#L293).

**New/modified assertions present:** `TestServePluginRequest` sends an oversized cookie POST without a CSRF header, asserts 413, and asserts the plugin handler was never called. The helper tests reject oversized form data, including a valid token at the start (no truncated-data acceptance), with `ErrorAs(*http.MaxBytesError)`. A separate new case sends an oversized body with a valid CSRF header and asserts success, no error and full body length still readable. Existing cases cover non-cookie/GET bypass, valid/invalid header, form CSRF, and strict versus legacy XMLHttpRequest behavior. [413/no dispatch](https://github.com/mattermost/mattermost/blob/4196a5a222e5536bc93584dcead452df138eee4b/server/channels/app/plugin_requests_test.go#L573); [oversize/form/header cases](https://github.com/mattermost/mattermost/blob/4196a5a222e5536bc93584dcead452df138eee4b/server/channels/app/plugin_requests_test.go#L669); [existing CSRF branches](https://github.com/mattermost/mattermost/blob/4196a5a222e5536bc93584dcead452df138eee4b/server/channels/app/plugin_requests_test.go#L615). These are server tests with httptest/mock handlers, not Cypress/Playwright E2E.

**Missing regression cases / limits:** No direct E2E cap assertion was located. The valuable next server cases are exact allowed-limit versus limit+1 (including the `bytes.MinRead` allowance), an injected non-size read error asserting 500 and no dispatch, and a below-limit form ensuring the plugin receives the identical original body. Existing GET/non-cookie cases use nil bodies, so they do not explicitly prove oversized body streaming on those paths. These suggestions should preserve the intentional header bypass, not change it into a security finding.

**Execution evidence:** None inspected; no test run performed here.
