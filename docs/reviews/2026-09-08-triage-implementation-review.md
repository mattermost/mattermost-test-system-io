# Triage implementation review — 2026-09-08

Scope: `apps/server/internal/triagework`, the report-provenance boundary needed by its trusted-master consumer, and the new Mattermost `triage-*` callers in `/private/tmp/mattermost-pr38356-demo`. Impact Gate was excluded. This was an independent review; implementing agents made the code fixes.

## Findings and disposition

| Finding | Concrete counterexample | Disposition after coordination and source recheck |
|---|---|---|
| Generated test code inherited host authority | The strict syntax checker accepted a new `node:fs` import and a `/proc` environment read alongside unchanged tests/assertions. The candidate then ran under the same Linux user as the credential-holding controller. Environment filtering did not isolate filesystem/process access. | Fixed: candidate execution moved to a separate Docker PID namespace, without a Docker socket or host PID sharing, with dropped capabilities, no new privileges, non-root user, read-only source/root filesystem, and only isolated result/runtime mounts. `sandboxArgs` has a passing authority/mount regression. The malicious source was only parsed during review, never executed. |
| Lease renewal and publication could race | `beat()` returned immediately while another renewal was pending; GitHub mutations continued after a failed heartbeat. A PR could be created before the server rejected the stale completion. | Fixed for the identified race: shared renewal is awaited; each GitHub mutation checks the fence and receives the abort signal. Publication uses a stable item branch, reconciles uncertain POST results through GET, and records its receipt before requesting reviewers. Per-mutation fence, uncertain PR response, and reviewer-failure regressions pass. External network uncertainty still requires reconciliation; cancellation is not proof that GitHub performed no operation. |
| Discovery could not enqueue | The caller sent an empty ticket while the handler and OpenAPI required a nonempty ticket. Every enqueue failed. | Fixed by an agreed contract change: ordinary enqueue permits an omitted ticket; the caller omits it and OpenAPI no longer requires it. Quarantine still requires its own tracking ticket. |
| Product-suspect work had no scheduled reconciliation | An initial Jira timeout left terminal product-suspect work unclaimable, while discovery discarded its enqueue response. Neither uncertain submissions nor later observations reached the defect API again. | Fixed: discovery handles product-suspect enqueue responses and calls the defect endpoint with the returned token. A protocol regression covers this route. |
| Older observations repeatedly failed reconciliation | Discovery processed newest and then older master observations. After advancing a product item, an older enqueue returned a legitimate stale-observation conflict on every scheduled run. | Fixed: discovery deduplicates the newest observation per framework, suite name, and stable key. The regression includes a later redundant observation. |
| Recovering an old closed Jira ticket consumed a new failure | G1 creation became uncertain; its Jira issue was subsequently closed; G2 then failed on master. Pending reconciliation linked G2 to the recovered closed G1 issue, so the recurrence guard prevented a new ticket. | Fixed in `triagework.reconcilePending`: recovery first links the original observation. A newer observation is attached only to a currently unresolved issue; recovery of a closed issue leaves the newer observation eligible for recurrence. PostgreSQL regression `closed_uncertain_older_Jira_does_not_consume_new_observation` passed. |
| Cypress sandbox omitted required bootstrap configuration | The isolated runner defaulted to `firstTest=false`, `resetBeforeTest=false`, and Team edition, while the trusted compose harness configured first-test/reset behavior and enterprise edition. | Fixed: an explicit allowlist carries the trusted generated compose configuration into the Cypress expose wrapper. A fixture checks bootstrap values and excludes unrelated credentials. |
| Registration claims did not establish ownership of uploaded bytes or metadata | Another uploader could replace JSON/screenshots after trusted registration, and group metadata could have been supplied first by another credential. Optional registration shard counts also could inherit an untrusted Begin declaration. | Fixed and source-rechecked after root integration: Begin commits its group and verified receipt together; Register commits its group, immutable registration receipt, owner, and verified claims together. Conflicting retries roll back group changes. Both upload endpoints check the immutable principal before streaming. The consumer requires matching verified source claims, uses a verified Begin receipt when the registration omits the shard count, and derives image/harness metadata from report receipts. The default source allowlist accepts the master on-merge workflow, excluding the PR dispatcher. Historical rows remain unverified. |
| Nullable shard predicates could be ignored | A missing count/receipt field produced SQL NULL for one shard. `bool_and` skipped it while accepting another true shard. | Fixed: each shard predicate is wrapped in `COALESCE(..., false)` inside `bool_and`; mixed-shard rejection passed in the final receipt-era PostgreSQL race run. |
| Jira dedup collapsed caught-product events | G1 and G2 linked to one unresolved issue produced one submission row, so listing submissions omitted the second caught occurrence. | Fixed: the defects list is driven by `triage_product_observations`, with optional linked submission details and explicit report-group identity. The PostgreSQL regression verifies three observation events despite two ticket submissions. |
